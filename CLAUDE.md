## Project Overview

Frame has two halves that share one Z3-backed separation-logic core:

1. **Solver** (`frame/core`, `encoding`, `checking`, ... below): a separation logic entailment checker for `P |- Q`.
2. **Security agent** (`frame/sil`, see "Security Scanner" below): tree-sitter frontends for Python, Java, JS/TS, C/C++ and C# lower source to SIL, a taint/heap analysis finds vulnerabilities, Z3 checks path feasibility, and an optional LLM layer adds detection, triage, exploitation (`frame exploit`) and fixing (`frame fix`).

The solver supports:
- Core separation logic: empty heap (`emp`), points-to (`x |-> y`), separating conjunction (`*`)
- Pure formulas: equality, boolean logic, arithmetic
- Inductive predicates: lists, trees, custom data structures
- Frame reasoning with automatic inference

## Documentation

Every user-facing feature also gets a runnable example in `examples/<name>/` (a small project, a README with the commands and their real output, offline data recorded with `examples/record_offline.py`). `tests/test_examples.py` runs each README's commands on a copy and checks the shown lines still appear. Scans inside Frame's own repository take `--root .` (a subdirectory scan otherwise indexes all of Frame for cross-file imports). `examples/` is excluded from the self-scan (its lockfiles are vulnerable on purpose).

User docs: `README.md`, `docs/usage.md` (every command, flag, config file and environment variable), `docs/dependencies.md` (SCA walkthrough), `docs/ai.md`, `docs/engine.md`, `docs/coverage.md`. Update them in the same commit as the feature, with examples taken from real runs. `tests/test_docs.py` fails when a CLI flag (usage.md; solver commands in engine.md) or a `FRAME_*` variable read in `frame/` is undocumented, or a relative link or `#anchor` is broken.

```bash
pip install -e ".[dev]"    # scanner grammars + pytest, xdist, ruff, mypy, benchmark deps
# Users install only: pip install -e ".[scan]"  (CI verifies this path in a clean venv)
```

if you add a language, add its grammar there too (missing grammars show up as ~300 failing
tests, not as one clear error).

## Security Scanner (`frame/sil`)

```
frame/sil/
├── frontends/      # tree-sitter -> SIL, one per language (python, java, javascript, c, csharp)
├── specs/          # per-language source/sink/sanitizer models (taint specs)
├── analyzers/      # interprocedural taint, path-sensitive, C/C++ heap lifecycle (SL), semantic patterns
├── translator.py   # SIL -> vulnerability checks
├── scanner.py      # FrameScanner: the pipeline (parse -> checks -> verify -> dedupe -> filter -> LLM -> suppress)
├── suppressions.py # inline `frame: ignore` markers + .frame.toml / [tool.frame] config
├── llm_*.py        # LLM detect / triage / exploit / fix / client (OpenAI-compatible, FRAME_LLM_* env)
└── cli.py          # `frame scan` implementation
```

- Symbolic findings and LLM findings are tiered separately (`source_var` = `llm_detect` / `llm_verified`); never merge the tiers.
- **Two argparse parsers exist**: `frame/cli.py` (the `frame` entrypoint) and `frame/sil/cli.py` (`python -m frame.sil.cli`). `cmd_scan` lives in `sil/cli.py`, but any new `scan` flag must be added to BOTH parsers (tests/test_cli_frame_entrypoint_excludes.py exists because this bit us).
- Suppression/config precedence: CLI flags > config file > built-in defaults. `--min-severity` and `--fail-on` default to `None` in argparse so the config file can supply them; resolve in `cmd_scan`.
- **The scanner reports every finding; benchmark scoring collapses** (`tests/test_scan_reporting.py`). `_deduplicate_vulnerabilities` keeps each distinct sink of a real function (same-CWE reports in one 5-line window merge as one flow), one finding per (file, CWE) for a synthetic file-wide pass (`<module-proto-pollution>` flags every matching line), and one per (file, line, CWE) across analyzers. Collapsing a real function to one finding per CWE hid a second injectable query added beside a known one -- invisible behind a baseline. One-label-per-file suites (OWASP, Juliet, IssueBlot) score `scanner.collapse_per_file_cwe`, applied in `benchmarks/core/sast_runner.run_frame_scanner` and `score_benchmarkjava.py`: one per (file, CWE), and an `html`-sink XSS dropped beside another finding in the same procedure. Never put benchmark-shaped filtering back in the scanner or translator (it used to hide a second SQLi endpoint, and every XSS in a handler that also had SQLi).
- `-l`/`-p` are defined once (`sil/cli.add_language_and_pattern_args`) and default to None: a directory scan walks `language_extensions(lang)` (every supported extension when no `-l`). `scanner.EXTENSION_LANGUAGES` / `language_for_file` is the single extension table (a `.h` using C++ syntax is `cpp`). Directory-target JSON is always the `{"files": [...]}` shape.
- **Incremental scans, baselines, verify** (`tests/test_incremental_scan.py`; `fingerprints.py`, `changes.py`, `verify.py`): every reported, suppressed and baselined finding gets `path` (relative to `project_root`: `--root`, else the git top level, else the Frame config's directory, else the scanned dir -- never the cwd, so it does not depend on where the scan runs from; a baseline whose paths do not exist under the resolved root warns via `baseline_root_mismatch`), an exact `fingerprint` (path, CWE, normalised function, source, sink kind, normalised line text, ordinal) and a `fingerprint_loose` (no line text). Never put a line number in either: insertions above a finding must not change its identity. `match_findings` pairs exact keys, then loose keys one-for-one by nearest line. `--changed [REF]`/`--files` narrow `scan_directory(only_files=...)`; nothing changed is a clean exit 0. `--baseline` moves known findings to `ScanResult.baselined` (in the JSON, never dropped) and lists vanished ones as `baseline.fixed`; `--write-baseline` replaces scanned files' entries and keeps the rest. `frame verify` matches against all of a file's earlier findings (including baselined/suppressed context from the JSON) and locates files under the JSON's `root`: a finding silenced by `frame: ignore` is `suppressed`, a same-CWE leftover is `uncertain`, and a file that cannot be found without a root is `unverifiable` -- never `fixed`/`file_removed` by accident. Scan exit status: 0 clean, 1 findings at/above `--fail-on`, 2 the scan could not run.
- **Cross-file taint** (Python, JS/TS; `tests/test_cross_file_taint.py`; `project.py`): a directory scan follows taint across imports -- request data a handler passes to a helper in another file reaches that file's sinks (reported IN the helper's file, with `data_flow` naming the call site), and a helper that returns request data taints its callers. `ProjectIndex` reads imports/exports with the frontends' tree-sitter parsers (no code runs): Python `import`/`from` (absolute by path-suffix match under a root the importer can see, relative, `__init__` re-exports, submodule-or-symbol `from pkg import x`), JS/TS `require`/destructured `require`/`import`/`export` (CommonJS and ES, barrels, `module.exports = fn` callable modules, default exports of named functions; relative specifiers only). The JS frontend already rewrites a call on an imported module to `<specifier>.<member>`; resolution maps that name back. Resolution is deliberately narrow and never guesses: plain functions through a resolvable import, plus methods whose receiver's class is known from evidence in the file -- `Class.static()`/`cls` methods, `x = C(...)`/`new C(...)`, `self.x = C()`, annotations and annotated constructor parameters (`self.repo = repo` copies the parameter's type; TS parameter properties), `C().m()`, base classes in the project, JS constructor functions (`this.m = ...`, `module.exports = Ctor`, `const C = require('./c')`). Also resolved: a function whose every non-null return builds one project class is a factory (`x = make_repo()`; `FileModule.factory_calls`, `_returned_class_text`; a cycle resolves to nothing), `from m import *` (public names or `__all__`; a local definition wins; a name two star imports bring stays unbound), tsconfig/jsconfig `paths` and `baseUrl`, and `import C from './c'; C.m()` (the default class's static method). A receiver with conflicting classes or of unknown type stays unresolved; so do package imports, anonymous default exports and ambiguous module names (they keep default argument->result propagation). `benchmarks/exemplars/` (README + `run_comparison.py`) is the living comparison against Semgrep/OpenGrep/Bandit/CodeQL on controlled cases and pinned real apps; add a use case there when you add a resolution shape. C/C++ are untouched (C has its own passes; C# is indexed with the Java family, see below). `ProjectContext.build` translates each file once (under the path string a lone scan would use, so `location` does not change), runs the fixpoint over all files, and the scanner reports file by file with the project's program and translator (`scan(..., program=, translator=)`). Directory scans do this by default (`--no-cross-file` opts out; a full scan over `--cross-file-limit` files, default 2000, falls back to per-file with a warning). `--changed`/`--files` widen to `ProjectIndex.closure`: the changed files, the files that (transitively) import them (their callee summaries changed), and everything those import (so each is analysed exactly as a full scan would -- a file analysed against a truncated view reports findings a full scan would not, so truncation warns). A baseline then filters what was already known, which is why `--changed` without `--baseline` reports pre-existing findings in the widened set. `frame verify` re-scans inside the same scope (JSON `scope.cross_file`): a helper finding that exists only because a caller passes request data is `present` while the caller still does, and re-scanning the helper alone would have called it `fixed`.
- **Java cross-file** (`tests/test_java_cross_file.py`, `exemplars/java/`): a directory scan indexes `.java` files (`ProjectIndex._read_java`: package, single-type and on-demand imports, each type's supertypes; a file gets an edge to the project files of every type it mentions, so `--changed` widens to the classes that use a changed one) and runs the same IPA fixpoint. The frontend records `Call.callee_class` (the receiver's declared type, a class name used as a qualifier, or the calling class for `m(x)`/`this.m(x)`, which may be inherited); `_resolve_call_instr` -> `ProjectContext.resolve_java_call` resolves it like the compiler: own file, explicit import, same package, on-demand import (a name imported from outside the project is not a project type), then the method on the class, else the nearest project supertype, else -- for an interface or abstract type -- the one concrete implementation (with two or more, the call resolves to none, but `_record_dispatch_entry_taints` passes the arguments' taint into every implementation, `java_dispatch_targets`; the result keeps default argument->result propagation). Overloads are chosen by argument type through `Program.resolve_java_call(assume_closed=True)` (the project has seen the supertypes); with no arity/type information a name with several overloads is not resolved. A nested expression call `Params.path(req)` resolves through its capitalised qualifier (`_resolve_callee`). `new X(args).m()` is lowered as the creation call (bound to a `$newN` temporary, a sink in its own right) then `$newN.m()`. The frontend's name-based one-hop param propagation (`_propagate_interprocedural_taint`) skips overloaded names. Project mode only: single-file Java scans are unchanged except for the creation-chain lowering and `ProcessBuilder` checking every argument.
- **Project root, closures, templates, evidence** (`tests/test_cross_file_taint.py`, `test_interprocedural_taint.py`, `test_template_aware_render.py`, `test_js_recall.py`): scanning a subdirectory still resolves imports rooted above it -- `_start_project` indexes the project root (`fingerprints.project_root`: `--root`, else git top) as context and reports only the scan target (`scope.context_root`; over the file limit it warns and scans the target alone). A nested JS function records the enclosing variables it reads (`Procedure.captures`) and its `parent`; the translator treats whatever attacker data those variables carry in the parent as entry taint of the closure (`_record_capture_taints`, flow-insensitive over the parent) and a call's return summary maps captured names back to the caller's state (`_arg_taint_leaves`, `_apply_return_summary`, `_closure_captured_vars` at sinks) -- NodeGoat's `find(searchCriteria())`. `res.render("view", {a, b})` is an XSS sink only for the data keys the template prints raw (`templates.py`: EJS `<%-`, Handlebars `{{{ }}}`, Nunjucks/Swig `| safe`, Pug `!=`; loop variables alias their source; includes and a sibling layout are read; an unreadable template, `autoescape false` or a spread keeps every value a sink); the frontend narrows both the Call's argument and the TaintSink (`_render_data_exps`). A JS/TS finding whose source is a `req.*`/`request.*` name and where neither the file nor the project shows a web framework (`framework_evidence.py`) carries `source_evidence: "naming-convention"` -- a tag, not a filter.
- **Known limits** (keep this list current; they come from `benchmarks/exemplars/`): the "+N other" counts for the other tools in the comparison are untriaged (`triage.json` labels Frame's and CodeQL's); JS function parameters are not sources by default, so library-style code that takes untrusted input as a parameter (`sast/seeds/sqli-concat.js`) is not flagged; an instance method is resolved through class evidence in the file (`R().m(x)`, `r = R(); r.m(x)`, a declared receiver type) or, across files, through the project index; the hold-out (`holdout/`) was keyed before Frame was run (first run 7/14, `first_run_frame.json`), so scores after the fixes it drove are not blind.
- **Hardening findings** (`hardening.py`, `tests/test_hardening.py`): configuration that switches a protection off, reported with `category: "hardening"` (never mixed into taint results or their precision), and only for an explicit off switch. The checks are data: a pack's `[[setting]]` entries (`kind` debug/cookie_secure/cookie_httponly; `at` kwarg/assignment (module level)/attribute/subscript/property; `keys`; the literal `value`; `call` or `receiver` globs), in `python/flask-settings`, `python/django-settings` (detected by `files`/`module_names`, detect keys for settings modules), `python/web-settings` (no detect) and `javascript/cookie-options`. `hardening.py` only matches the entries of the packs applied to the file. `frame inventory` lists a pack as a framework only if it has rules, entrypoints or lambda handlers. A missing option is not reported (defaults differ per library); missing rate limiting / CSRF tokens are policy queries and are not implemented.
- **Guards that clear findings** (`tests/test_js_recall.py`): a redirect target is safe after `startsWith('/') && !startsWith('//')` (either shape) or when it starts with a constant `/path`; membership in a constant allowlist (`Object.values(CONST).includes(x)`, `CONST.includes(x)`, `x in CONST`; UPPER_CASE names only) sanitizes `x` for every sink kind; `jwt.verify` is not a sink (`jwt.decode` is); `shell-escape`/`shell-quote` sanitize shell kinds. Sink specs keyed on a first string argument (`crypto.createHash('md5')`, `createCipheriv('des...` as a prefix) are matched by `_arg_qualified_spec`; a call assigned to a variable (`const rows = this.db.query(...)`) honours member-chain suffixes like a standalone call. In JS/TS a request read inside an assigned object literal or stored on an object (`filter.origin = req.body.tags`) taints the object (`_taint_from_embedded_sources`; JS/TS only -- the Python frontend lowers dict literals differently).
- **Dependency graph** (`frame/sca/`, `frame deps`, `tests/test_sca_lockfiles.py`): readers per format in `lockfiles.py` return a `DependencyFile` (packages keyed `ecosystem:normalised-name@version`, edges, warnings); `discover.read_dependencies` reads every lockfile and a manifest only when no lockfile of its ecosystem is in the same directory. Never guess: `direct` is None unless the lockfile or the manifest beside it says (`mark_direct`), and dev-only comes from the lockfile's own flags (`DEV_FLAGGED`) or, for formats without them, from reachability over the edges (`_propagate_dev`). YAML lockfiles go through `_yaml.py` (the block subset package managers write; anything else is a `YamlError`), XML with a DOCTYPE is refused, and a file that cannot be read is a warning, never an abort. Ecosystem names are OSV's (`PyPI`, `npm`, `Maven`, `NuGet`, `Go`, `crates.io`, `SwiftURL` named by repository host/path). Go, Rust and Swift are read for dependencies only (Frame does not scan their source); `go.mod` and `Package.resolved` have no edges, so they are in `DEV_FLAGGED` (reachability would mark every indirect module dev only). Build-tool reports (`jvm.py`: `maven_dep_tree.txt`/`.json`, `gradle-dependencies.txt`) and `obj/project.assets.json` stand in for a lockfile of their directory. Gradle build scripts are read without Gradle (`gradle.py`, `tests/test_sca_gradle.py`: declarations, script/`ext`/`gradle.properties` variables, the version catalog); a report covers the build files of every module beneath it. Their declared names must equal Gradle's direct set on the `sca-real` fixtures. `apply._gradle_edit` edits a literal coordinate written once, else the catalog edit after which `read_catalog` shows only that library moved; anything else is manual. `frame deps --resolve` (`resolve.py`; tests use stand-in executables on PATH) runs `mvn dependency:tree` once per topmost pom, Gradle `dependencies` for every project, and `pip install --dry-run --report --only-binary :all:`; it is opt-in because it runs the project's build code, and never runs during a scan.
- **`frame scan --sca`** (`frame/sca/scan.py`, `tests/test_sca_scan.py`): `prepare` reads the graph and matches the cached advisories (never fetches), `sink_packs` turns each advisory's functions into a generated pack (`Rule.only_if_not_sink`: a sink only where no built-in spec or pack already makes the call one, so `yaml.load` keeps CWE-502), `link` joins a finding to an advisory only when the finding's `sink_call` is that function at that call site (`Vulnerability.sink_call`, internal, filled by `_note_sink_call` after each instruction and set explicitly for nested sinks). Off without `--sca`, so scans and benchmarks are unchanged. Nested sink calls (`f(g(req.query.n))`) also read sources written inline in their arguments (`_get_embedded_member_sources`), as the TaintSink path does.
- **Upgrade plans** (`frame/sca/plan.py`, `ranges.py`, `tests/test_sca_plan.py`): the target is the lowest advisory-named fixed version >= current that no advisory for the package affects (offline). The action comes from `DependencyFile.requires` (requiring package key, "" for the project -> name -> declared range), filled by the lockfile readers and, for the project's own ranges, the manifest beside the lockfile. `satisfies` per registry (node-semver incl. its prerelease rule, PEP 440 incl. Poetry ^/~, NuGet/Maven intervals, Maven soft requirements, Cargo default caret); it returns None for what is not a range, and the tests pin agreement with node-semver and `packaging`, so change range code only against them. Compare against `packaging` only on final/post releases: its default pre-release handling differs between versions (CI's pip vendors a newer one than local), so pre-release rules are pinned to the PEP 440 text.
- **Applying plans** (`frame/sca/apply.py`, `tests/test_sca_apply.py`): edits are textual and minimal (only a version, or a new override entry), shown as a diff and written only with `--apply`; anything not safely editable is `manual`, never approximated. `pyproject.toml` edits are section-aware (PEP 621 dependency arrays, Poetry dependency tables) so keywords or descriptions naming a package are never touched. A manifest without a lockfile, Maven and `go.mod` are always edited (their versions are the requirements; re-running Maven resolves the same thing). `--relock` runs the package manager; the live npm test runs in `sca-real`.
- **Breaking-change adaptation** (`frame/sca/adapt.py`, `tests/test_sca_adapt.py`; `--adapt` with `--verify`): runs only when the project's command passed before and fails after the upgrade; the model sees the output and the files importing the upgraded packages (`usage_files`), edits only application source (`_editable`: no manifests, lockfiles, or paths outside the root); kept only if the command passes and the re-scan of edited files adds no finding type (an unscannable file fails closed). Release notes (`notes.py`) come from the repository the registry names: the changelog file at the target's tag sliced by version headings (`slice_changelog`), else GitHub release bodies; feature releases first; a fetch failure means no notes. Tests inject `proposer=`, `run=` and `notes=`; the live test needs `FRAME_LLM_*`.
- **Dependency mitigation** (`frame/sca/mitigate.py`, `tests/test_sca_mitigate.py`; `frame fix DIR --deps`): verification re-runs the full `--sca` analysis on a resolved temp copy of the project with the patch (never one file: a cross-file flow must still be seen), and accepts only `removed`/`untainted` with no new finding in the file; tests inject proposals (`proposer=`), the engine is real. Guards that pin a value to constants (`_EXACT_VALUE_KINDS`: membership, `strcmp ==`) also clear `vulnerable_dependency`; character-class guards deliberately do not. Paths are compared resolved (`scan._rel`), or macOS `/var` vs `/private/var` hides findings.
- **Constant tables** (`source_facts.constant_tables`, `tests/test_constant_tables.py`; Python, JS/TS): a name bound exactly once in the file to a dict/object/list/tuple/set literal of literals (no f-strings, template substitutions, spreads, computed keys) and never written into or rebound (subscript/member writes, mutating methods, `Object.assign`, parameters, loop targets, a second binding) or passed to a call outside a small read-only set. `TABLE[key]` and `TABLE.get(key)` take no taint from the key (`_constant_table_index`; `.get`'s default still counts). Read from the tree-sitter syntax tree, not text.
- **VEX** (`frame/sca/vex.py`, `tests/test_sca_vex.py`): statements follow evidence: present = `affected` (CycloneDX `in_triage`), tainted = `exploitable`, `not_affected` only from `.frame/vex.toml` decisions (strictly validated; matched by any alias; stale ones warned) or `--dev-not-shipped`, and a recorded `not_affected` against a tainted flow is refused (kept `affected`, conflict reported, exit 1 in `frame deps --vex`). Outputs are validated against the official OpenVEX and CycloneDX 1.6 schemas committed in `tests/fixtures/sca/schemas/` (with format checking); keep them validating.
- **SBOM** (`frame/sca/sbom.py`, `tests/test_sca_sbom.py`): CycloneDX 1.6 / SPDX 2.3 from `read_dependencies`; packages merged by purl across manifests, dev = `scope: optional` / `DEV_DEPENDENCY_OF`, edges = `dependencies` / `DEPENDS_ON`. Licences only from evidence (`Package.license`: npm and Composer lockfiles, or `licenses.enrich` from installed metadata of the same version, `license_source: installed`), with SPDX ids from package data (`frame/sca/data/spdx-license-ids.txt`), never from test fixtures. Every real-tool fixture's SBOM is schema-validated. A Maven report covers the poms of the modules beneath it (no version-less duplicates).
- **Z3 upgrade planning** (`frame/sca/solve.py`, `registry.py`, `tests/test_sca_solve.py`; `frame deps --plan --registry`, npm, PyPI, crates.io and NuGet): scope = vulnerable packages plus all ancestors; candidates = current + newer stable non-deprecated registry versions; `present_p` models a package leaving the tree; the current version's ranges are the lockfile's where recorded, else the registry's, and a range known nowhere holds the child (never `*`); a candidate whose dependencies are unknown is never chosen; optional crates count as built; Cargo re-locks package by package, retried in dependency order; "no vulnerable version" is soft (weight 1000), ranges are hard; minimise majors, raised requirements, changes (leaving the tree counts), distance of direct then of the rest, in that order. NuGet is `LOWEST_APPLICABLE`: a transitive package equals the lowest candidate every present holder admits, and a NuGet plan is never `update-lockfile` (re-locking moves nothing; `override` / `raise-requirement` instead). Go has no solver (MVS over a complete go.mod); `GoRegistry.go_directive` reads each target's `go` line from the proxy and `_go_toolchains` adds `requires_go` / `within_go` (the newest fix the module's `go` builds). `plan.fixable`: an advisory with no fixed version never blocks a target and is listed in `unfixed`. Unresolved packages keep their per-package plan (override). The real-app fixture's answer is re-checked by plain code, and live by applying and re-locking with npm (in `sca-real`). Registry metadata is fetched only with `--registry` and cached (`FRAME_REGISTRY_CACHE`).
- **Configuration mitigations** (`frame/sca/mitigations.py`, `tests/test_sca_mitigations.py`): curated entries (`data/mitigations/<Ecosystem>.json`, dataset `mitigations/` wins per advisory) are validated strictly: `versions` (the registry's range syntax), `complete`, a `caveat` for partial ones, `references` (the evidence: the advisory text, the library's source at a tag). Never add one from memory. Settings are read where the application gets them (Dockerfile CMD/ENTRYPOINT/ENV, Compose, Kubernetes with `kind`/`apiVersion`, systemd, shell, `.env`, named properties files, Java `System.setProperty` and curated calls from the syntax tree via `mine._parser`; `spring-property` ways from `application*`/`bootstrap*` .properties/.yml (flattened), `-D`, `--k=v` java arguments and the env name Spring binds, compared under relaxed binding, `_relaxed`/`spring_env_name`); build-time JVM settings never count. Found mitigations are VEX notes, never `not_affected`. YAML is PyYAML `safe_load_all` (in the `scan` extra).
- **Licence policy** (`frame/sca/licenses.py`, `tests/test_sca_licenses.py`; `frame deps --licenses`): SPDX expressions are parsed (AND binds tighter than OR, WITH exceptions) and evaluated three-valued (ok / violation / unknown; OR passes if any choice is ok, AND fails if any part is a violation). A non-SPDX licence is unknown unless a deny entry names it; trove classifiers are not mapped. `[licenses]` in the Frame config is strict (deny, allow, unknown, include_dev). The live test compares with `pnpm licenses list`. Registry licences (`licreg.py`, `--registry`) only from a version's own record, never package-level or latest; live tests compare with each `.gem`'s metadata (not `gem specification --remote`, which reads a reduced index), `cargo metadata`, each nuspec, and Maven's effective POM (POM licences inherit from the parent; free text maps to SPDX only through SPDX's own list, fetched under `--registry`, not shipped: a URL or name two ids share does not decide).
- **Fix-commit mining** (`frame/sca/mine.py`, `tests/test_sca_mine.py`, recorded real commits in `tests/fixtures/sca/commits/`): never guess an id. - **Frontend conventions that bit us** (each was a silent recall or precision bug):
  - Code that is not inside a function must still be lowered. JS module scope becomes a synthetic `<module>` procedure; string-literal class fields / object properties become `<clinit>` / `<literal-properties>` procedures (`frontends/_literal_fields.py`). These carry only `Assign`s of literals, so they add no taint sources or sinks.
  - Spec sink-kind strings must go through `instructions.resolve_sink_kind` (aliases such as `path` -> `filesystem`, `redos` -> `regex`). Every frontend does; a hand-rolled `if kind in SinkKind else SQL_QUERY` fallback used to report any unrecognised kind (a tainted `setHeader`, a tainted regex) as SQL injection. A new spec sink kind must be a `SinkKind` value or an alias -- `tests/test_sink_kind_resolution.py` fails otherwise. What each kind reports, its aliases, and each finding type's CWE and category are data (`specs/data/kinds.toml`, loaded by `frame/sil/kinds.py`; `tests/test_kinds.py`): a new `SinkKind` or `VulnType` needs its entry there, or every scan fails.
  - Path conditions are joined disjunctively in **every** language, and the walk does not follow an edge the solver proves infeasible (`_edge_feasible`). Without that pruning a provably dead path can be the first to reach a join and the feasible one is never analysed (salt `archive.py`); see `tests/test_join_path_conditions.py`.
  - `ProcSpec.is_source` taints only the call's *return value*. C input functions that fill a buffer or out-parameter (`fgets`, `scanf`, `read`, `recv`) use `taint_out_args` (set in `c_specs.py`).
  - C vs C++ matter: `Program.language` is `"c"` or `"cpp"`. A bare variable argument can only be an out-parameter in C++ (reference binding); in C it is a by-value read (see `_arg_may_define`).
  - **C/C++ path facts are decided by the SL/Z3 checker, never by name sets.** The path condition is a list of pure formulas: branch guards (`_feasibility_guard`), `x == rhs` for assignments (`_assignment_fact`), with writes, stores through pointers and calls havocking what they may change (`_advance_path_facts`). Joins keep `shared & (rest1 | rest2)` (`_join_path_conditions`). CWE-476 is `pc |- p == nil` (`_provably_null`), decided after a dedicated path-fact fixpoint (`_path_fact_fixpoint`) because the main walk does not re-analyse a node when only its path condition changes. Do not add per-pointer flag sets; add facts.
  - CWE-190 too: `_note_overflow_candidates` (at each C assignment) records a `*`/`+`/constant-`<<` with attacker data in an operand whose declared type is in `_INT_TYPES` (`Procedure.scalar_types`, plain variables only; `long`/`size_t` are not guessed), and `_confirm_path_candidates` reports it when `pc & operand ranges & result > MAX` is satisfiable (MAX of the type after the usual arithmetic conversions). Weak-random data and IPA seeds are not candidates. The same candidates cover CWE-191 (`-`/`*` below MIN), CWE-197 (`_note_truncation_candidate`: assigned to a narrower declared type) and CWE-194/195 (`_note_size_arg_candidates`: a signed value that can be negative at a `size_args` position of the c/cpp tables; 194 when narrower than `int`). Adding a spec row turns off default argument->result propagation for that call, so a fact goes on an existing row or comes with its propagation.
  - CWE-457 uses the same machinery: "x has no value yet" is the ghost fact `x#uninit == 1` (set by a bare declaration, cleared by anything `_uninit_inits` counts as a write), and a read is reported only if `pc & x#uninit == 1` is satisfiable (`_maybe_uninitialized`). The walk's reaching-definition set only nominates candidates.
  - A write or a call **forgets atoms, not facts** (`_forget`): only the atoms about the changed names become unknown (true where positive, false under a negation), so a disjunction keeps what it says about other variables. An oversized join first forgets volatile atoms (fields, globals, call results; see `_is_stable_name`) before falling back to the shared facts. For C, guard formulas use real arithmetic over the variables with casts stripped (`_exp_to_formula`), never an opaque name like `"(n % 4)"`. C guards that clear taint (`_c_equality_fact`, in `_guard_vars`): `strcmp(x, "lit") == 0` (or `!strcmp`), `strspn(x, "set") == strlen(x)` over a safe charset, and `strncmp(x, P, strlen(P)) == 0` with P a `scheme://host/` literal or string macro (`Program.string_macros`; ssrf/redirect). A destination buffer (`snprintf`, `strcpy`) keeps the sanitization every tainted source had, including a sanitizer wrapped around it (`atoi(req)`). A lookup (`find`, `at`, ...) in a local initialised with a brace list of literals returns no taint from the key (`_literal_tables`). `memcpy`/`memmove`/`bcopy` sink on the LENGTH, discharged when a path guard mentions it (`_copy_size_sink`). `sprintf` into a fixed buffer is CWE-120 when a `%s` argument holds attacker data and the longest output (literal text, each `%s` source's capacity or precision, widest numeric conversions) exceeds the destination (`_tainted_format_overflow_checks`). File-scope arrays have bounds (`Program.global_array_bounds`) for the tainted-index check when no local shadows them. C++ constructor initializer lists are lowered as member assignments, and a member's allocator kind from the constructors (`_member_alloc_kind`) is checked when another method releases it (CWE-762). The SL memory analyzers drop the heap effects of a branch that always exits (`return`/`exit`/`goto`), so a free on that branch does not make the later free a double free. A `for` loop that walks every character of a string and leaves the path at the first one failing a character-class test (`isalnum`, `isdigit`, ...) is followed by a `Sanitize` of that string for every sink (`_validation_loop_var`); `Sanitize` is an annotation, not a write, so it keeps the path facts. Weak randomness (C): `rand()`/`random()`/`drand48()`... are `TaintKind.WEAK_RANDOM` sources; `SinkKind.UNPREDICTABLE` (CWE-338) marks values that must be unpredictable (`EVP_*Init*` key/IV, `HMAC` key, `PKCS5_PBKDF2_HMAC` salt, `RAND_seed`, and any argument of a header writer whose literal names `Set-Cookie`, `_cookie_header_checks`). `_create_taint_check` marks a check whose taint kind does not fit (weak-random data at any other sink, other data at an UNPREDICTABLE one) and `translate_procedure` drops it. A C store (`buf[i] = v`) taints `buf` (weak update; a source call inside v counts), a C function that leaves taint in a buffer parameter records it as `param_fields[p][""]` and the caller's argument receives it (`_apply_filled_buffers`), and `n = strlen(buf)` adds `0 <= n <= N-1` for a fixed array of N (`_length_bound_facts`). Constants: an assignment that is not a literal records the variable in `SymbolicState.nonconst`, and a constant known on one side of a join survives only if the other side did not assign the variable something else; before this, `i` stayed `0` through `i = i + 1` and code after `for (i = 0; i < N; i++)` was never reached.
  - C++ `if`/`while`/`switch` conditions are `condition_clause` nodes in tree-sitter-cpp: `_translate_expression` and `_translate_effects` unwrap them (before, every C++ guard reached the solver as an opaque name). `T &r = x;` with x a local or parameter is an alias: later uses of r are lowered as x (`_note_reference_alias`, `_alias_of`). A call inside an expression is its own Call only when it must be (`_delivers_into_arguments`): it fills an argument (`taint_out_args`), is a usage sink (`sink_args = []`), or has an `algorithm_arg`; otherwise it is an `ExpCall` carrying its return value. `<limits.h>`/`<stdint.h>` constants are integers to the solver (`c_int_model.LIMITS`, seeded under the file's own `#define`s in `_int_macros`), consistent with the type widths the range checks use (`c_int_model.INT_TYPES`).
  - **The C frontend must lower every write and every jump**, or the path facts describe paths that do not exist: `break`/`continue` are real edges (`_translate_jump`, with a `for` update node as the `continue` target; a `break` inside the sequentially-lowered `switch` stays a no-op); `#if`/`#ifdef` inside a function body becomes an unguarded branch per arm (`#if 0` arms are dead; no `#else` means an empty arm); comma expressions and nested `x++`/`--x` are lowered (postfix through a `$` temporary); `x += e` is `x = x + e`; an assignment inside a condition is an `Assign` in the node that evaluates it (loop conditions in the loop head). Function-like macros `#define`d in the file are recorded on `Program.function_macros` and may write their arguments.
  - The scanner's `_verify_check` runs the incorrectness checker (`pc * null_deref(p)` -> witness). It used to raise on every call (stale `VulnType` names) so nothing was verified; `tests/test_c_null_path_facts.py` pins it.
  - C analyzers are structural passes (translator, SIL-based) plus the class-lifecycle and SL heap analyzers in `interprocedural_analyzer.py`, `sl_memory_analyzer.py` and `sl_semantic_analyzer.py` (some still read lines). The 2,900-line `_detect_semantic_cwes` fallback is gone (roadmap step 7): never add a rule keyed on a variable's name or a line of text; use a spec fact, a solver question or the syntax tree. Test C snippets one statement per line all the same.
- **A spec name is not always the whole story** (`tests/test_sink_receiver_precision.py`):
  - Frontends and `Program.get_spec` suffix-match member chains (`models.sequelize.query` -> `query`). A global function spec (`setTimeout`, `eval`, bare `exec`/`execSync`/`spawn`) sets `ProcSpec.global_only`: a member call matches only on `window`/`global`/`globalThis` or a receiver the file never declares (`_may_be_global`), so `req.setTimeout(ms, cb)` and `re.exec(s)` are not sinks.
  - JS module bindings (`const cp = require('child_process')`, `import {exec as run} from ...`) rename calls after the module in `_get_call_name` (`cp.exec` -> `child_process.exec`, `run` -> `child_process.exec`), so module-qualified specs match whatever the local name is.
  - A guessed receiver type (`Program.get_spec`'s common-prefix list) never yields a taint-free usage sink or an `exact_class` spec. Credential-named variables whose head noun is metadata (`secretKeyAlgorithm`) are not secrets (`_METADATA_HEADS`; the name rules, value shapes and word lists are data in `specs/data/secret-names.toml`, `tests/test_secret_names.py`). Python-only idioms (pathlib `/`) are gated on `program.language`.
  - A sink that installs a callback (`setHostnameVerifier`) sets `permissive_callback_arg`: it fires only when the callback provably accepts everything (all returns `true`, or a documented-permissive library object, also through a non-reassigned local/field).
  - Java `catch` clauses are branches after the try body (`_translate_handlers`), not code that always runs, and `throw` is a value-less `Return`. Sequential handlers made a rethrowing catch end every path and a helper "return" its exception.
  - XXE: `secure_parsers` holds parsers hardened by `setFeature`/`setAttribute`/`setEntityResolver` (`_track_xml_hardening`; the features, attributes and the lxml and deserializer settings are `specs/data/parser-hardening.toml`), products of a hardened factory, and results of a same-class helper whose every non-null return is hardened (summarised in a pre-pass). Joins intersect it and `_states_equal` compares it. `TaintSink.receiver` carries the parser to the sink.
- **Java specs match by declared type** (`tests/test_java_declared_types.py`): many keys are written against a conventional variable name (`documentBuilder.parse`, `jdbcTemplate.query`). The frontend records each name's declared type (fields, params, locals, for-each/resource/catch vars; `var` from `new T()` or `JAVA_FACTORY_RETURN_TYPES`; a name declared with two types is unknown) and sets `Call.receiver_type`; `typed_spec_lookup` (used by the frontend and `Program.spec_for_call`) tries `type_spec_receivers(T)` (`T`, decapitalised `T`, `JAVA_TYPE_RECEIVERS` aliases) before names. An `exact_class` spec (`Random.*`) needs the runtime class (`Call.receiver_exact`: `new T()`, never reassigned) because a value declared `Random` may be a SecureRandom; a taint-free name-only sink is not applied to a receiver whose type is known. Session/request `getAttribute` is server state, not a source.
- **Same-named procedures are all kept** (`tests/test_overloaded_procedures.py`): `Program.add_procedure` names the 2nd, 3rd... `name#2`, `name#3` (overloads, Python property setters, C `#ifdef` arms) instead of replacing the first, and records `overload_arities`; use `Procedure.simple_name` and `accepts_arity(n)` for arity-only languages.
  - Java calls resolve by type (`Program.resolve_java_call`): the frontend types each argument (`_arg_type`: literals, primitives/arrays/fields, numeric promotion, casts, `new`, own-method return types, String methods) and each parameter (`_static_type`, type variables unknown); `java_convertible` says yes/no/maybe (widening, boxing, final JDK types, the in-file hierarchy `Program.class_supertypes`). An exact match wins; otherwise a single non-rejected candidate wins only in a class with no supertypes (`Procedure.class_open`), since an inherited overload could be more specific. Anything else resolves to nothing -- never guess.
- **JS NoSQL sinks are database-handle methods** (`ProcSpec.db_method`, `db_method_applies`): they need a receiver (`RECEIVER_UNKNOWN` marks a chained call's), and do not apply when the frontend's `_receiver_kind` knows the receiver is something else -- an array/string/regex/object/function literal, `new X()`, a value from a Node core module or an in-memory utility library (`crypto.createHash(...)`), an array/string method result, an object-literal property, or a call whose first argument is a function literal. Unknown receivers (a model imported from `./models/user`) still match.
- Java lowers a call in a `return` expression as `tmp = call; return tmp`, and hoists an argument that is a taint-source call (`parse(req.getInputStream())` -> `$a = req.getInputStream(); parse($a)`), so specs and ordinary propagation apply. An unqualified / `this.` call to a method the class declares resolves to that procedure (`receiver_type` = the class), never to a same-named library spec, and `spec_for_call` returns None for it so default argument->result propagation still applies (returning the procedure's empty ProcSpec silently disabled it and cost ~20 points of OWASP recall).

- **Inline sources and nested sinks** (`tests/test_python_recall.py`, `tests/test_js_recall.py`): tree-sitter-python's `typed_parameter` has no `name` field (the name is its first child), so read it there or every annotated parameter is lost. A bare subscript of a source container in a sink (`request.args["d"]`) matches `<chain>.__getitem__`; wrapped in any call it does not. `_get_embedded_source_calls(exp, sink_kind)` stops at a sanitizer for that sink, and the Call path checks both inline source calls and sink calls nested in its arguments (`new BufferedReader(new FileReader(p))`). `ProcSpec` widens a `shell`/`command` sanitizer to both kinds (`shlex.quote` covers `os.system`). Python `request.user` / `.session` / `.auth` are server state (`_is_request_server_state`); so are JS `req.session.*` (not a source: it is what the server stored), also when destructured (`({ session }, res)`); both lists are `specs/data/request-objects.toml`. aiohttp/Starlette/Sanic request accessors are sources; statement-level `await f()` is lowered like `f()`; a `%` format with a tuple/dict right operand carries the taint of its members. - **Inter-procedural taint within one file** (Python, JS/TS; `tests/test_interprocedural_taint.py`): Java already taints String params and C/C++ have their own passes, so `_ipa_applies` gates this to Python, JS/TS and C# files where some procedure calls another of the file's procedures. `translate_program` runs the analysis to a fixpoint FIRST with checks discarded (a caller analysed before its callee would report with the callee's effects unknown, and a check cannot be withdrawn), then the real reporting pass, which is READ-ONLY on the summaries (so results never depend on the order files are reported in). The fixpoint (`run_ipa_fixpoint`) is a worklist, not rounds: every procedure once, then only those whose entry taints or used return summaries changed, bounded by a visit budget that sets `IPAState.incomplete` (reported as `scope.complete: false`) -- a round cap silently lost chains deeper than the cap whenever file names sorted against the call direction. `_resolve_callee` resolves `f(...)` and `self.`/`this.`/`cls.` methods in this file (never an unknown-typed `obj.m`, a shared name, or a procedure whose own spec already says source/sink/sanitizer), and -- in a project -- a function of another file the call's name resolves to through the imports. Summaries are keyed by `ProcRef = (file key, proc name)`. Two summaries flow: entry taints (`_record_entry_taints`: a call passing attacker data taints the callee's parameter, sanitized only for kinds EVERY such call sanitized) seeded in `_init_state_for_procedure`, and `ReturnSummary` (`_accumulate_return`: the callee's own source, plus which parameters reach its return and the kinds every path sanitized them for) applied at call sites (`_apply_return_summary`) and inside expressions (`_arg_taint_leaves`, `_get_embedded_source_calls`, `_summary_inline_sanitized`). While summarising, every unseeded param carries a `@param:`-prefixed SEED taint so a return summary is learned before any caller passes real taint; seeds are never reported nor recorded as entry taint. A third summary, `ReturnSummary.stores`, records which parameters a method stores into a receiver field (`this.f = p` / `self.f = p`, `_accumulate_store`). At a call site, `new C(v)` / `C(v)` (constructors resolve through `_resolve_constructor`, or Java/C# `<init>`) or `x.setF(v)` with attacker data in v taints `x.f` in the caller (`_apply_field_stores`; a plain copy `y = x` replaces y's field taints with x's), and a later `x.m()` seeds `this.f` (plus `self.f`, and the bare `f` in Java/C#/C++) as entry taint of m (`_record_field_entry_taints`). Object-sensitive per local variable, never per class. A taint sink also matches a tainted field path written in its expression (`self.options.additional.join(..)`, `_field_chains`). In library mode (SecBench), each method of a JS class starts with the fields its constructor fills from its parameters tainted (`_constructor_field_paths`: a function `C` with `C.prototype.m` methods, or an ES class `constructor`). Assigning a plain local is a strong update (`_exec_assign`): its taint, sanitization and asserted safety are dropped first unless the right-hand side reads it. `is_sanitized_for`/`is_asserted_safe_for` compare sink kinds through `_SINK_KIND_ALIASES`. A ternary (`ExpTernary`; Python lowers `a if c else b` to it) takes the branch its condition folds to over the path's constants (`_fold_condition`, which also folds the `ExpStringConcat` Python uses for every `+`), else the taint of either branch, never the condition's. Two more summaries ride on the same keys: a Python `@property` whose return carries attacker data taints `x.<property>` when `x` is created from its class (`_apply_property_sources`), and `ReturnSummary.param_fields` records the fields a procedure leaves tainted on a parameter (`req.filter = req.query.filter`); `app.use(mw)` turns mw's request fields into `IPAState.middleware_fields` for that app object, which every handler passed to the same object (`Procedure.passed_as`) receives on its first parameter (`_record_middleware`). Registration order is ignored. A `request.setAttribute("k", v)` inside a class implementing `javax`/`jakarta.servlet.Filter` with attacker data in v makes every `getAttribute("k")` on a servlet request in the project read it (`IPAState.request_attributes`; applied after the receiver's own propagation so a seed cannot overwrite it). C# binds `var x = new T(...)` to a `new T` call (types with no spec only) and hoists `new T(a).m()` into `$newN = new T(a); $newN.m()`; Java/C# constructors resolve as `<init>`/`ctor` and are never looked up on a supertype; a bare-name write to a field in `Program.declared_fields` counts as a store. A Java/C# call on the result of a project method resolves through the method's declared return type (`Tool.of(..).run(v)`, `_value_class`). C#: a type declared in several files is one partial class (`ProjectIndex.java_partials`; a method is looked up in every part), an unqualified call inside a class method is looked up on the caller's class, and `x.M()` resolves to a project extension method (`Procedure.is_extension`, `resolve_extension`: one visible through the file's namespaces, the receiver passed as the first argument). Python/JS: an instance another module builds at its top level and this one imports resolves through that module's evidence (`_imported_instance_class`: `repo = Repo()`, `module.exports = new Mailer()`, `container = { reporter: new Reporter() }` read as `container.reporter`, a class-body `objects = PostManager()` read as `Post.objects`); `module.exports = require("./q")` and `{ ...require("./q") }` are star re-exports; a call through a module-level `functools.partial(f, a)` resolves to f with the bound arguments prepended as untainted placeholders (`resolve_partial`); `require("m").f(...)` is named `m.f` like a call through a bound alias. `ExpCall`-nested calls (no Call instr) are handled by `_record_nested_entry_taints`. A numeric conversion is a sanitizer for every text-payload injection (`_NUMERIC_SAFE`: JS `parseInt`/`Number`/...). Property-assignment sinks are not applied in Python (`response.raw = x` is not Django `Manager.raw()`).

- **Secret formats** (`frame/sil/secret_formats.py`, `specs/data/secret-formats.toml`, `tests/test_secret_formats.py`): provider credential formats as data, each with `reference` (the provider's documentation) and `ignore` (published example values); only formats with a fixed provider prefix and length (no Stripe test keys, no bare JWTs). `FrameScanner._scan_provider_tokens` reads string literals from the tree-sitter tree of the file's language (never comments) and reports any containing a format, whatever holds it. JS `tool(name, x, schema, handler)`: x is a description only when string-shaped. Never judge wording. Tool handlers carry `Procedure.entry_kinds` (`mcp-servers:tool`, set by `packs.apply`); `frame inventory` lists `mcp_tools` with `capabilities` (sink kinds reached by the handler and same-file callees).
- **Test code** (`frame/sil/test_code.py`, `tests/test_test_code.py`): from the program, never the file name: test-framework imports (`Program.imports`), JUnit/TestNG `@Test` (canonical or written whole), C# test attributes, a module-level Python `test_*` with its own `assert` (`Procedure.asserts`, set by the Python frontend), JS procedures `passed_as` to `describe`/`it`/`test`. `_tag_test_code` sets `Vulnerability.context = "test"` (JSON, SARIF, text) on every finding of the file; only a name-based `hardcoded_secret` (procedure not `<literal>`) drops to low.

- **AI applications** (`packs/data/{python,javascript}/llm-sdks.toml`, `mcp-servers.toml`; exemplars in `benchmarks/exemplars/frameworks/*/llm-sdks`, `*/mcp-servers`): `TaintKind.LLM_OUTPUT` (`llm`) is model output and MCP tool arguments; `SinkKind.PROMPT` (CWE-1427) is a model's system instructions only (Anthropic `system`, OpenAI `instructions`, LangChain `SystemMessage`, and a role/content message dict/object whose role is the literal `system`/`developer`: both frontends emit `<chat-system-message>(content)` for it before each simple statement, `_system_message_instrs`, nested functions skipped, and the LLM packs make that name a prompt sink; never a user turn). `TaintKind.RETRIEVED` (`retrieved`, the `llm-context` packs: LangChain vector-store searches by method name, `retriever.invoke` by conventional receiver name, MCP client `call_tool`/`read_resource`/`get_prompt`) is handled like `llm` (category `ai`, dropped at confidentiality sinks): indirect prompt injection. Entry points mark each name a destructuring parameter binds (`packs/apply.bound_names`).
- **Known limits (this stretch)**: `.cshtml`/`.razor` are not scanned; a pack rule does not apply to a procedure defined in the same file; Java `ProcessBuilder` flags tainted trailing arguments as command-line injection (argument injection) by design.
- **Known limits (e2e expansion)** (strict xfails in `tests/e2e/test_known_gaps_*.py`): Weak randomness (every language) is CWE-338 where an API needs an unpredictable value or where the destination's name says so (`unpredictable.toml` `[destinations]`, see "CWE-338 by destination"); never because a file includes a crypto header. - **Weak randomness by flow** (`tests/test_weak_random_flow.py`): Python/JS/Java PRNG calls are `is_source = "weak_random"` (Java's `Random.*` are `exact_class`; `new T().m()` has an exact receiver); `Random.nextBytes` / `random.shuffle` fill their argument (`taint_out_args` honoured outside C for `weak_random`). Where a value must be unpredictable is data, not specs (`specs/data/unpredictable.toml`, `specs/unpredictable.py`: canonical ids or trailing names, positions and keywords), checked by `_unpredictable_arg_checks` (also for calls nested in arguments and for inline source calls). Inline source calls never become a check of another kind (`_inline_kind_mismatch`), and a source call nested in a call's arguments taints its result by the call's own propagation rules. C# keeps per-call CWE-330. The OWASP Python harness passes `benchmarks/packs/` (its `helpers.utils.mysession` is a session store); never put such a pack in `frame/sil/packs/data`.
- **C library facts** (`frame/sil/c_facts.py`, `tests/test_c_facts.py`): the c/cpp spec tables say which functions allocate (`allocates`: heap, stack, mapped, new, new_array; `allocates_via` for an out-parameter like posix_memalign), release (`frees`, by the kind they release; never stack), never return (`noreturn`) or read through which pointer arguments (`dereferences`, -1 for every one); the memory analyzers and the translator take their sets from `c_facts` (plain identifiers only: several analyzers put names into regexes), never from lists of their own. Benchmark-harness functions (Juliet's `printLine`) belong in `benchmarks/packs`, never in an analyzer.
- The JavaScript type model (`_value_kind`: Node core modules, in-memory libraries, database-handle factories, builtin method result kinds, global constructors and factories) is `specs/data/javascript-types.toml`.
- The Java type model (receiver aliases, factory and chain return types, `String` method result types, permissive verifiers, the javax -> jakarta moves) is `specs/data/java-types.toml`, exposed by `java_specs.py` under the old names; JLS numeric promotion stays code.
- Adding sources/sinks: edit `frame/sil/specs/data/<table>.toml` (python, javascript, java, csharp, c, cpp): one `[[spec]]` per call name, in lookup order, with the `ProcSpec` fields that differ from their defaults. `specs/tables.py` loads them strictly (an unknown field or a name listed twice is an error) and the `*_specs.py` modules only expose the tables (plus the Java type tables in `java_specs.py`). The knowledge base can ship `specs/<table>.toml`; a table in the last pulled revision replaces the built-in one (spec tables load once per process, so they follow the cache's current revision, not a project lockfile).

## Architecture (solver)

The codebase is organized into logical modules for better maintainability:

```
frame/
├── core/           # Core abstractions (AST, parser)
├── encoding/       # Z3 SMT encoding
├── checking/       # Entailment checking and heuristics
├── analysis/       # Formula analysis and reasoning
├── heap/           # Heap graph and pattern detection
├── folding/        # Predicate folding/unfolding
├── arithmetic/     # Arithmetic reasoning
├── preprocessing/  # Formula preprocessing
├── predicates/     # Inductive predicate definitions
├── lemmas/         # Lemma library
└── utils/          # Utilities and proof management
```

### Core Components

**frame/core/ast.py** - Abstract Syntax Tree
- Defines all formula types: `Expr`, `Formula`, `Var`, `Const`, `ArithExpr`
- Spatial formulas: `Emp`, `PointsTo`, `SepConj`, `Wand`
- Pure formulas: `And`, `Or`, `Not`, `Eq`, `Neq`, `True_`, `False_`
- Quantifiers: `Exists`, `Forall`
- Predicate calls: `PredicateCall`

**frame/core/parser.py** - Parser
- Converts string formulas to AST
- Two-stage: Lexer tokenizes, Parser builds AST
- Supports entailment syntax: `"P |- Q"` for parsing both sides
- Handles precedence: quantifiers > disjunction > conjunction > separating conjunction

**frame/encoding/encoder.py** - Z3 Encoding
- Encodes separation logic formulas to Z3 SMT constraints
- Heap represented as Z3 array from locations to values
- Explicit domain tracking for allocated locations
- Key methods:
  - `encode_expr()`: Converts AST expressions to Z3
  - `encode_heap_assertion()`: Encodes spatial formulas with disjointness
  - `encode_pure()`: Encodes pure boolean/arithmetic constraints
- Delegates spatial encoding to `frame/encoding/_spatial.py`

**frame/checking/checker.py** - Entailment Checker
- Main interface: `EntailmentChecker` class
- Algorithm:
  1. Parse formulas to AST
  2. Unfold predicates (bounded, depth 3 default)
  3. Encode to Z3 with heap + domain tracking
  4. Check validity: `P |- Q` is valid if `P & !Q` is unsat
- Fast paths:
  - Reflexivity check (syntactic equality)
  - Heuristic checks before Z3 (via `frame/checking/heuristics.py`)
- Adaptive unfolding based on formula complexity
- Returns `EntailmentResult` with validity, model, and reason

**frame/predicates/** - Inductive Predicates
- `base.py`: `InductivePredicate` abstract base class
- `registry.py`: `PredicateRegistry` manages available predicates
- Built-in predicates:
  - `ListSegment`: `ls(x, y)` - list segment from x to y
  - `LinkedList`: `list(x)` - null-terminated list
  - `Tree`: `tree(x)` - binary tree
  - `DoublyLinkedList`: `dll(x, p, y, n)` - doubly-linked list
- `PredicateValidator`: Checks soundness (strict positivity, free variables, arity)
- `GenericPredicate`: Creates predicates from SMT2 definitions

**frame/lemmas/** - Lemma Library
- `base.py`: Core lemma library with pattern matching and application
- `_matcher.py`: Pattern matching for lemma application (meta-variables)
- `_substitution.py`: Substitution and equality normalization
- Proven lemmas for common predicates (e.g., list segment transitivity)
- Used to prove entailments without unfolding
- Key lemmas:
  - `ls_transitivity`: `ls(x,y) * ls(y,z) |- ls(x,z)`
  - `ls_cons`: `x |-> y * ls(y,z) |- ls(x,z)`
  - `ls_empty`: `ls(x,x) |- emp`

### Data Flow

1. **String Input** → Parser → AST
2. **AST** → Predicate Unfolding (recursive, bounded depth)
3. **Unfolded AST** → Z3 Encoder → SMT Constraints
4. **SMT Constraints** → Z3 Solver → SAT/UNSAT
5. **SAT/UNSAT** → EntailmentResult (valid/invalid + model/reason)

### Key Design Decisions

**Theoretical Foundation**: Frame implements separation logic (Reynolds & O'Hearn, 2002) using SMT-based reasoning with Z3. The core technique is the heap-as-array encoding (Piskac, Wies, Zufferey, 2013), which reduces separation logic entailments to first-order logic queries. See README.md "Theoretical Foundations" section for detailed references and comparison with other solvers (Sleek, Cyclist, Grasshopper, SPEN).

**Heap Representation**: Heap is a Z3 array `heap: Loc -> Val`. Domain is tracked as a set of locations. Disjointness enforced by ensuring domains don't overlap in separating conjunction.

**Predicate Unfolding**: Bounded unfolding (default depth 3) to maintain decidability. Deeper unfolding increases completeness but may hit recursion limits or timeouts. Adaptive unfolding adjusts depth based on formula size.

**Predicate Folding**: Goal-directed folding prioritizes proposals that match the consequent (inspired by Cyclist's cyclic proof techniques but adapted for SMT). Blind folding provides a fallback for general synthesis.

**Lemma Library**: Pattern-based lemma application (similar to Sleek's strategy) handles common entailments without Z3 queries. Proven lemmas for transitivity, reflexivity, and construction patterns.

**Soundness**: All predicates validated for strict positivity (no negation), free variables properly bound, and arity consistency. Parser bug fixed in commit d239d01 - critical fix for storing body text correctly.

**Performance**: Fast paths for reflexivity (<1ms), syntactic checks before Z3. Average 5ms per check on test suite.

## Critical Implementation Notes

### Parser Bug Fix (d239d01)
The parser had a critical bug where it was storing the Formula object instead of the body text when parsing SMT2 predicates. This caused recursive predicate definitions to fail. Always store `body_text` as string, not Formula object.

### Recursion Handling (2233a73)
Predicates with deep recursion can hit Python's recursion limit. The checker now handles `RecursionError` gracefully by returning `unknown` instead of crashing. Consider increasing unfold depth carefully.

### PTO Syntax (3ba90de)
The parser handles SMT2 syntax `(as nil Type)` in struct fields for points-to assertions. This is essential for SL-COMP benchmarks where nil values are typed.

### Wand Implementation
Magic wand (`P -* Q`) is NOT commutative unlike other binary connectives. Handle carefully in syntactic equality checks and encoding.

### Separation of Concerns: Lemmas vs Folding (Critical Architecture)

**IMPORTANT**: Lemmas and folding serve fundamentally different purposes and must NEVER be mixed:

**Lemmas** (`frame/lemmas/`):
- Proven facts about predicates (e.g., `ls(x,y) * ls(y,z) |- ls(x,z)`)
- Apply to predicate calls that already exist in the formula
- Pattern matching against existing structure
- Fast, deterministic application
- Located in `frame/lemmas/base.py` and category files

**Folding** (`frame/folding/`):
- SYNTHESIS of predicates from concrete heap structures
- Converts points-to assertions into predicate calls
- Graph-based pattern detection and proposal generation
- Heuristic, confidence-based selection
- Located in `frame/folding/goal_directed.py` for entailment checking

**Checker Integration Order** (`frame/checking/checker.py`):
1. Goal-directed folding: `fold_towards_goal()` - synthesizes predicates matching consequent
2. Lemma application: `try_apply_lemma()` - applies proven facts about existing predicates

**Why This Separation Matters**:
- Previously, Phase 3 folding was embedded in `LemmaLibrary.try_apply_lemma()`, violating separation of concerns
- This made lemmas responsible for both pattern matching AND synthesis
- Caused confusion about what lemmas should do
- Made the codebase harder to maintain and extend
- The refactoring in November 2025 properly separated these concerns

**When implementing new features**:
- Proven predicate transformations → Add to lemmas
- Heap pattern synthesis → Add to folding module
- Never add folding logic to lemma library
- Never add lemma-style pattern matching to folding (use graph patterns instead)

## Common Issues

**Unfold Depth Too Low**: If entailment should be valid but returns invalid, try increasing `registry.max_unfold_depth`. Symptoms: predicates need deeper unfolding to match.

**Timeout**: Complex formulas may timeout. Increase `timeout` parameter or simplify formula. Check if predicate definitions are efficient.

**Parser Errors**: Ensure formulas use correct syntax. Check `frame/core/parser.py` for supported grammar. Common issues: missing parentheses, wrong operator precedence.

**Predicate Validation**: Custom predicates must pass soundness checks. If validation fails, review strict positivity, free variables, and arity consistency.
